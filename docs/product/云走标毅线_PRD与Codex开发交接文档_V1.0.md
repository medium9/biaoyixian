# 云走标毅线｜产品需求与 Codex 开发交接文档

**版本：** V1.0  
**项目类型：** Web 轻量级多人在线虚拟徒步应用  
**产品阶段：** 第一版 MVP  
**开发方式：** AI 辅助开发（Codex）  
**文档状态：** 第一版开发基准

---

# 一、项目概述

## 1.1 项目背景

「云走标毅线」是一个以杭州经典徒步路线——标毅线为基础的线上虚拟徒步项目。

项目参考线上《清明上河图》、线上虚拟寺庙等轻量级互联网创意项目。

用户通过浏览器进入一个共享的二维地图，创建自己的虚拟徒步身份，选择起点和行走节奏，随后人物自动沿标毅线移动。

所有用户共享同一张地图。

用户可以看到其他在线徒步者，彼此打招呼、互动、称赞。

走完整条路线后，用户获得电子纪念凭证，并累计个人完成次数。

项目希望构建一个轻量、有趣、可以反复参与的线上公共徒步空间。

## 1.2 产品定位

一个所有人都可以参与的杭州标毅线线上徒步世界。

核心关键词：

- 二维地图
- 虚拟徒步
- 多人在线
- 自由行走
- 陌生人互动
- 完赛纪念
- 累计挑战

## 1.3 产品目标

第一期实现：

1. 用户可以注册和登录。
2. 用户拥有自己的虚拟人物。
3. 用户可以选择徒步起点。
4. 用户可以选择不同的行走速度。
5. 人物能够沿标毅线自动移动。
6. 所有在线用户能够出现在同一张地图上。
7. 用户可以与其他徒步者互动。
8. 完成挑战后获得纪念凭证。
9. 系统记录累计完成次数和收到的称赞。

## 1.4 非目标

第一期不做：

- 手机 App。
- 微信小程序。
- 3D 场景。
- 手绘山水长卷。
- 复杂游戏引擎。
- 真实 GPS 定位。
- 真实运动步数统计。
- 复杂装备和人物养成。
- 商城和交易。
- 自由聊天、私信、好友系统。
- 复杂排行榜。
- AI NPC 或 AI 聊天机器人。

本项目的核心是地图、人物移动和在线互动，不是开发一款大型网络游戏。

# 二、整体产品形态

## 2.1 运行平台

第一期采用 Web 网页版。

用户通过浏览器访问网址即可使用。

要求：

- PC 浏览器优先。
- 兼容手机浏览器。
- 不需要下载安装。
- 地图支持鼠标拖动、滚轮缩放。
- 手机支持触控拖动和双指缩放。

## 2.2 核心界面

整个产品以一张二维地图作为主界面。

地图占据网页主要显示区域。

建议界面布局：

### 顶部区域

显示：

- 产品名称：云走标毅线。
- 用户昵称。
- 当前行走模式。
- 当前行走距离。
- 当前路线进度。
- 在线人数（真实在线人数）。

### 中央区域

显示：

- 杭州真实二维地图。
- 西湖。
- 钱塘江。
- 西湖群山。
- 标毅线完整路线。
- 沿途中文地名。
- 用户虚拟人物。
- 其他在线徒步者。

### 辅助操作区域

提供：

- 开始。
- 暂停。
- 继续。
- 行走模式切换。
- 地图缩放。
- 个人资料。
- 互动操作。

不需要将地图做成传统网站的内容管理页面。

用户进入网页后，应该直接看到地图和正在行走的人。

# 三、地图设计规范

## 3.1 地图基本要求

采用真实地理地图作为底图。

第一期不使用手绘山水插画作为地图底图。

地图要求：

1. 二维平面地图。
2. 默认北朝上。
3. 地理位置准确。
4. 支持自由缩放。
5. 支持地图拖动。
6. 支持路线覆盖。
7. 支持自定义人物标记。
8. 支持人物聚合。
9. 支持中文地名标签。

地图需要体现杭州的地域特征。

重点显示：

- 西湖。
- 钱塘江。
- 西湖群山。
- 标毅线。
- 沿途山峰。
- 主要寺庙和文化景点。

## 3.2 地图技术方向

优先评估高德地图 JS API 2.0。

官方文档：

https://lbs.amap.com/api/javascript-api-v2/summary

地图引擎需要支持：

- 地图缩放。
- 地图拖动。
- Polyline 路线绘制。
- 自定义 Marker。
- Marker 聚合。
- 地图事件监听。
- 地理坐标与屏幕坐标转换。

注意：

地图服务的授权、配额及正式商业使用条件需要在上线前核实。

不能擅自抓取地图瓦片并重新存储、分发。

需要统一地图坐标系，避免 WGS84、GCJ-02 等坐标混用造成偏移。

# 五、用户系统

## 5.1 注册与登录

用户可以注册账号并登录。

用户资料至少包括：

- 用户ID。
- 登录凭证。
- 昵称。
- 虚拟人物形象。
- 注册时间。
- 累计完赛次数。
- 收到的称赞次数。

登录后，用户拥有一个长期保存的线上徒步身份。

## 5.2 虚拟人物

每个用户在地图上对应一个虚拟人物。

第一期采用简单的二维人物图标即可。

要求：

- 能够区分不同用户。
- 有简单行走状态。
- 不需要复杂人物建模。
- 不需要复杂人物装扮系统。

# 六、行走模式与移动机制

## 6.1 行走模式

用户开始徒步前，可以选择三种模式。

| 模式 | 虚拟全程时间 | 平均虚拟速度 |
|---|---:|---:|
| 跑山 | 3 小时 | 约 8.19 km/h |
| 徒步 | 6 小时 | 约 4.10 km/h |
| 慢走 | 9 小时 | 约 2.73 km/h |

计算基准：24.57 公里。

这些都是虚拟移动参数，不代表用户真实运动速度。

## 6.2 行走模式界面

用户点击开始之前，显示：

- 跑山：3小时。
- 徒步：6小时。
- 慢走：9小时。

默认推荐徒步模式。

用户自行选择。

## 6.3 自动行走

用户点击开始后，人物自动沿标毅线移动。

系统根据路线进度计算人物当前经纬度。

人物位置必须与地图路线保持一致。

不能让人物脱离路线自由漂移。

## 6.4 暂停和继续

用户可以随时暂停。

暂停后：

- 人物停止移动。
- 有效行走时间停止累计。
- 路线进度保存。

继续后：

- 从原位置恢复。
- 按当前行走模式继续移动。

## 6.5 网页关闭

用户关闭网页或退出登录：

- 自动停止当前移动。
- 保存路线位置。
- 保存累计有效行走时间。
- 保留当前挑战状态。

重新登录后可以继续。

## 6.6 切换模式

产品方向允许用户在徒步过程中调整行走节奏。

例如：

跑山 → 徒步 → 慢走。

切换后改变后续移动速度，不重置已经走过的路线进度。

具体切换交互和是否允许切换后的完赛时间仍需在实现前确认。

## 6.7 移动计算

建议采用路线累计距离作为进度参数。

系统需要：

1. 读取路线坐标。
2. 计算路线累计距离。
3. 根据有效行走时间和模式计算当前进度。
4. 根据路线进度找到对应的路线坐标。
5. 更新人物地图位置。

不要通过每次刷新页面简单增加固定经纬度来移动人物。

# 七、多人在线地图

## 7.1 核心原则

所有用户共享同一张地图。

每个用户有独立的虚拟位置。

用户开始行走后，人物沿着同一条标毅线移动。

不同用户可以处于不同路段。

例如：

- 用户A：老和山。
- 用户B：北高峰。
- 用户C：十里琅珰。
- 用户D：五云山。
- 用户E：玉皇山。

他们同时显示在同一张地图上。

## 7.2 在线状态

地图只将真实在线用户显示为在线人物。

用户关闭网页或退出后，不再作为在线移动人物展示。

可以保留其历史挑战记录和个人资料，但不得把离线用户伪装成在线用户。

## 7.3 人物聚合

地图需要支持缩放聚合。

缩小时：

多个距离接近的人物合并显示为人数圆点。

例如：

- 12人。
- 26人。
- 58人。

放大后：

人数圆点逐渐展开为独立人物。

能够看到各自昵称和位置。

聚合仅改变显示方式，不改变任何用户真实的虚拟位置。

## 7.4 人物交互

点击某个在线人物，弹出个人信息：

- 昵称。
- 当前路线段。
- 累计完赛次数。
- 称赞次数。

可以执行：

- 打招呼。
- 加油。
- 称赞。

第一期不开放自由聊天。

# 八、社交互动

## 8.1 打招呼

提供预设互动动作：

- 挥手。
- 你好。
- 加油。
- 一起走。

用户点击后，可以让对方看到简单的互动提示。

## 8.2 称赞

用户可以称赞其他徒步者。

称赞对象可以是：

- 累计完成次数较多的用户。
- 路上偶遇的用户。
- 个人资料中的其他徒步者。

系统累计称赞次数。

建议同一用户对同一对象设置合理的重复称赞限制，防止刷赞。

具体限制策略由后端实现阶段确定。

# 九、完赛机制与纪念凭证

## 9.1 完赛

用户完成标准标毅线全程后，系统记录一次完赛。

## 9.2 完赛凭证

生成一张电子纪念凭证。

凭证内容：

- 产品名称：云走标毅线。
- 用户昵称。
- 完成日期。
- 本次挑战次数。
- 本次行走模式。
- 本次累计有效用时。
- 路线名称。
- 路线距离。

## 9.3 累计完赛次数

用户每完成一次完整挑战，累计次数增加1。

例如：

- 第1次完成。
- 第2次完成。
- 第10次完成。
- 第20次完成。

个人资料中显示累计完赛次数。

## 9.4 完赛次数真实性

不能仅仅因为用户从路线中段走到终点，就计为完成一次全程。

需要完整覆盖标准路线。

**自选起点与全程挑战如何兼容，是当前待确认的核心业务规则。**

建议将自由漫游和正式全程挑战区分开：

- 自由漫游：允许任意位置进入和行走，但不自动计入全程完赛。
- 全程挑战：按照统一规则覆盖整条24.57公里路线后，才计入完赛。

具体如何支持从任意起点完成全程，需要产品确认后实现。

# 十一、技术架构建议

第一期采用轻量 Web 架构。

## 11.1 前端

优先考虑：

- Vue 3（如果现有项目没有既定技术栈）。
- 地图 JS API。
- 自定义 Marker。
- 路线 Polyline。
- 地图聚合组件。

如果现有项目已经有成熟技术栈，优先沿用，不要为了这份文档强制重构。

## 11.2 地图

优先评估：

高德地图 JS API 2.0。

地图负责：

- 地理底图。
- 路线绘制。
- 人物定位。
- 地图缩放。
- Marker 聚合。

## 11.3 后端

需要具备：

- 用户认证。
- 用户资料存储。
- 徒步进度持久化。
- 完赛记录。
- 称赞记录。
- 在线状态同步。

可评估 Supabase 等托管后端服务。

## 11.4 实时通信

多人在线功能需要实时通信能力。

优先考虑托管实时服务，避免第一期自行开发复杂游戏服务器。

实际位置更新频率应根据用户数量和服务成本优化。

不需要每秒向所有用户广播大量数据。

# 十二、开发阶段安排

必须分阶段开发。

不要一次性完成全部业务。

## 阶段0：数据与规则准备

目标：

准备真实地图和路线数据。

任务：

2. 获取或独立整理合法可用的GPS轨迹。
3. 核实路线关键节点。
4. 核实沿途景点经纬度。
5. 确定地图服务及授权。
6. 确认自选起点与全程挑战规则。

交付物：

- 标准路线GeoJSON。
- 地标JSON。
- 路线节点表。
- 地图数据来源及授权记录。

如果真实GPS文件尚未取得，可以使用明确标记为测试数据的临时轨迹进行阶段1开发，但不能将临时轨迹冒充真实标毅线。

## 阶段1：地图与移动原型

这是第一阶段实际开发目标。

先不做注册和完整业务后端。

功能：

1. 加载二维杭州地图。
2. 展示西湖和钱塘江。
3. 绘制标毅线。
4. 显示中文路线标签。
5. 显示沿途景点。
6. 地图拖动和缩放。
7. 生成20个测试人物。
8. 测试人物沿路线移动。
9. 实现跑山、徒步、慢走三种速度。
10. 实现人物聚合。
11. 点击人物显示简单信息。

注意：测试人物是开发模拟数据，不是真实在线用户。

验收标准：

- 地图位置关系正确。
- 路线能够完整展示。
- 中文标签能够正常显示。
- 人物不会偏离路线。
- 放大缩小时人物位置保持正确。
- 多人聚合和展开正常。
- 三种移动速度有明显区别。
- 页面运行流畅。

阶段1完成后，先由产品方验收，再决定是否进入阶段2。

# 十三、Codex 开发约束

以下内容必须遵守。

## 13.1 开发前

首先检查当前项目仓库。

确认：

- 是否已有项目。
- 使用什么前端框架。
- 是否已有后端。
- 是否已有数据库。
- 是否已有地图相关代码。
- 当前目录结构。
- 已有功能和依赖。

不要未经检查就新建一套项目覆盖现有内容。

## 13.2 开发原则

1. 优先实现最小可用功能。
2. 不擅自增加业务需求。
3. 不擅自删除明确提出的功能。
4. 不制作复杂3D场景。
5. 不制作手绘山水地图。
6. 不虚构真实路线坐标。
7. 不虚构真实在线用户。
8. 不把临时测试数据混入正式业务数据。
9. 不擅自接入未经确认的付费服务。
10. 不修改无关模块。

## 13.3 代码质量

要求：

- 代码结构清晰。
- 组件职责明确。
- 地图数据独立管理。
- 路线数据独立管理。
- 人物数据独立管理。
- 用户数据独立管理。
- 核心移动逻辑可复用。
- 方便后续扩展。

## 13.4 开发流程

Codex 首先：

1. 检查项目现状。
2. 输出项目结构分析。
3. 提出第一阶段实施方案。
4. 明确需要的地图数据。
5. 列出潜在风险和外部依赖。

然后先完成阶段1。

不要未经产品方确认就继续开发阶段2和阶段3。
